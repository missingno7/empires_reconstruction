## Known tool limitations (class (c) sources)

This scanner is a heuristic text scan, not a real C parser or preprocessor. The
following categories recur across the (c) verdicts above and are NOT bugs in the
ported code:

1. **Macro member-aliases are invisible.** `portable/generated/game_data.h` and
   `game_state.h` emit whole-object aliases as C `#define OLD NEW` (tracked by
   `symbols.json`'s per-symbol `aliases` list, which this tool DOES normalise
   through) but also emit *member-level* aliases like
   `#define g235d (g2356.text)` that are not in that list at all -- this tool has
   no C preprocessor, so `g235d` and `g2356.text` compare as different globals.
2. **Type names leak into the global-reference set.** A cast (`(uintptr_t)x`), a
   `struct TAG` use, or a macro-aliased struct tag (`struct gc0fe_record` for
   `struct menu_record`) is not a global object, but this tool's bare-identifier
   scan cannot always tell a type name from a reference; `NOT_A_CALL`/`C_KEYWORDS`
   list the common ones, but project-specific typedefs are not exhaustively
   covered.
3. **Local declarations the heuristic doesn't recognise.** `collect_local_names`
   only binds declarations that start with a hardcoded type keyword; a
   project-specific typedef (`menu_row_callback_fn *cbs;`), a `union {...} t;`
   with-body local, or an otherwise-shaped declaration is missed, so that local's
   name leaks into the global-reference diff for that function.
4. **Inline-asm operand symbols are masked out entirely**, not resolved. Turbo C
   `asm mov [gc0ea],bx` really does reference the global `gc0ea`, but this tool
   cannot safely parse asm operand syntax for symbol names (bracket/plus
   arithmetic, segment overrides), so it blanks the whole statement; a ported
   function that reads the same global through ordinary C syntax then shows up
   as an 'extra' global-ref, not a real diff.

## f9402 -- the bug that triggered this audit

`src/PUZZLE.C:228` (`void f9402(int i) { ... hud_prompt_message_draw((char far *)g0dc8 + g0dc8[i] + 2, flag); }`) calls the historical 2-argument `hud_prompt_message_draw` (defined `src/HUDPMSG.C:1`, `void hud_prompt_message_draw(p, a) char *p; int a;`). `portable/game/puzzle.c` had instead called `hud_prompt_message_run` -- an unrelated 1-argument function defined in `src/PROMPTS.C:79` that blocks on a keypress, a completely different control-flow shape from the fire-and-forget draw call `f9402` needs.

**Before** (portable/game/puzzle.c, prior to commit 1d8cfb6):
```c
hud_prompt_message_run((dos_char *)((dos_char *)g0dc8 + g0dc8[i] + 2));
```
**After** (current, commit 1d8cfb6 -- verified still correct by this audit):
```c
hud_prompt_message_draw((dos_char *)((dos_char *)g0dc8 + g0dc8[i] + 2), flag);
```

This audit's mechanical scan of ALL 55 ported units found no other instance of
this class of error (wrong callee name and/or wrong argument count at a call
site): every argc mismatch and every missing/extra call this tool flagged (listed
per-unit above) was investigated against both sources and is either an
intentional, documented port replacement **(b)** or a false positive of this
tool's heuristic text scan **(c)**. See 'Verdict counts' above.
